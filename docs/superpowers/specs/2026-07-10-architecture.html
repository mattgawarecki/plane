A visibility + control surface over live agent runs

Three questions answer the whole system: how does the backend move run state to the browser, how does the frontend put it on the page, and where do the two meet. The single fact that colours everything below: the live path today is HTTP polling — not WebSockets, not SSE.

Transport

How run state reaches the browser

Read this as: polling now, WS shim dormant, SSE later.
LIVE NOW

HTTP polling

The open panel re-GETs the full run snapshot every 2500 ms; a separate ambient count refreshes every 45 s (SWR). No push — the client asks, repeatedly.

agents-panel.tsx · setInterval(store.loadRuns, 2500)
use-agent-count.ts · useSWR(refreshInterval: 45000)

DORMANT

WebSocket shim

A real new WebSocket(...) transport is written and compiles, but the panel mounts it with { enabled: false }, so no socket ever opens. Present, wired, switched off.

transport/agents/agent-event-transport.ts · browser-socket.ts
useAgentSubscription({ enabled: false })

PLANNED

SSE (not built)

The intended upgrade is server-sent events to replace polling with a push stream. No EventSource code exists yet — it is a direction, not an implementation.

Backend · how it runs

A Node bridge over a live LLM loop

Bridge: a plain node:http server on :4000 holding one in-memory TAgentCollectionState (no journal file). Runtime: the Anthropic Tool Runner on claude-opus-4-8 drives 7 Plane tools; irreversible closes block on a human approval gate.

The runtime emits TAgentEvents → the bridge folds them with applyEvent into the state the panel polls.

The spine

Three layers around one shared vocabulary

The pure core @plane/agents sits in the middle and depends on nothing. The backend wraps it to produce events; the web layer wraps it to project them into UI. Crucially the same reducer runs on both ends — the bridge folds events into its state and the browser folds snapshots into its store using the identical applyEvent / reconcile functions.

Data flow

Two directions across the HTTP seam

Run state flows one way (backend → panel, pulled by the poll) and commands flow the reverse (panel → backend). Reversible controls (pause/resume/cancel) paint an optimistic status overlay that the next poll reconciles; approve/reject never guess — they resolve a parked promise or flip a status on the bridge, and the resulting state comes back on the next poll. The server stays the one source of truth. The green edge is the live HTTP boundary.

Observe

A run changes — the panel sees it on the next poll

backend → panel · pulled

The Tool Runner drives tools; each tool call emits a sequence-stamped TAgentEvent. The bridge folds events into its in-memory state and serves it over HTTP. The panel re-GETs that snapshot every 2500ms and reconciles it into the MobX projection. (The WebSocket transport would carry these events as a push instead — but it is dormant.)

Key concepts

Five things to hold in your head

The live path is polling

The panel re-GETs a full snapshot every 2500ms; the count refreshes every 45s. A WebSocket transport exists but mounts with enabled:false; SSE is the intended future replacement, not built. Say “polling now.”

One reducer, both ends

@plane/agents owns the types, the two interfaces, and the reducer. The same applyEvent / reconcile runs on the bridge to build state and in the browser to project it. Change the contract and every layer moves together.

The client is a projection

Local state is never authoritative — it is fully rebuildable from a listRuns snapshot. Refresh, reboot, reconnect all reduce to the normal poll path via reconcile, keyed by run id.

Human-in-the-loop gate

bulk_close can't mutate until a human taps Approve. The gate lives inside the tool's run, blocking on requestApproval — the panel's approval UX is the LLM's safety rail. It's the only irreversible tool.

Flag-gated, no core edits

Everything enters through @/plane-web and mounts at two seams. VITE_ENABLE_AGENTS === "1" is checked before any poll — flag-off is byte-for-byte today, zero network.
